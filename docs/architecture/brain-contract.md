## One implementable stack and its dependencies

Use Python 3.12, Django 5.2, a private SQLite database/evidence directory on a persistent local disk, and Caddy in Docker Compose on one founder-controlled Linux host. Django supplies password handling, sessions, migrations and permission primitives; we implement company/object authorization. Serve a small browser interface for setup, map/search, evidence/history, pending questions and corrections. Use one application process, short `IMMEDIATE` write transactions and bounded retry; never hold a transaction while invoking a model or channel. SQLite has concurrency limits, so concurrent intake/answer/retry tests must pass before a pilot-size claim. No Redis, vector database or separate frontend build is needed initially. This is a pilot deployment choice, not a scale claim. [Django authentication](https://docs.djangoproject.com/en/5.2/topics/auth/default/), [SQLite limitations and transactions](https://docs.djangoproject.com/en/5.2/ref/databases/#sqlite-notes).

Deploy path: supplied `deploy/brain/compose.yaml` starts the application and Caddy; only Caddy exposes 80/443, the database and evidence stay on private volumes, and Caddy proxies the configured public DNS name to the application. Founder bootstrap creates the owner locally on the host, with no public bootstrap endpoint. A hostname pointing to the host and reachable 80/443 are prerequisites for public certificate automation. Deployment must enforce HTTPS, secure cookies, CSRF, trusted hosts and production settings. [Caddy HTTPS prerequisites](https://caddyserver.com/docs/automatic-https), [Django deployment checks](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

**Unresolved dependency:** an exact authorized staging host/domain is needed to demonstrate remote access; the founder later needs control of the company host/domain, backup destination and operating cost. No account, provider, price, remote-host authorization or purchase is established. Do not reuse the operator's unrelated Nora/Supabase credentials or infrastructure by inference. Building and testing locally may proceed after leader authorization; a local API, Docker launch or deployment recipe does not meet Q2's online proof.

Deployment must include delivered automated consistent SQLite backups plus evidence manifests, encrypted transfer to an approved off-host destination, backup-health visibility and an executable restore command tested into a clean isolated instance. Caddy handles certificate renewal; delivered host setup configures automatic security updates and health checks. Application upgrades/migrations use a versioned operator procedure with backup and rollback. The founder chooses an operating owner and backup account; neither is assigned yet. Normal founder/team work must not depend on manual backups, daily server commands or assistant-authored administration. If no maintained hosting/operating arrangement is accepted, the self-hosted recommendation has an unresolved delivery gap; escalate that choice rather than burying server administration in founder setup. Backup implementation and restore evidence remain E0 here.

Interpretation runs automatically on the participant's computer using their already-authenticated Claude CLI, called by the delivered worker with supplied evidence/context on stdin, print mode, JSON-schema output and a validated `structured_output` response. Use an isolated empty working directory, safe configuration, built-in tools disabled and MCP tools explicitly denied; do not inherit project hooks/tools. Use an argument array, timeout and output limit. Record CLI/model/schema/prompt versions and source hashes. No shell evaluation of captured text and no API-key/billing fallback. Account availability, subscription limits, installed CLI flags and interpretation quality must pass setup and runtime probes; failures remain visibly queued. This is a proposed dependency, not a tested integration. [Programmatic execution and output validation](https://code.claude.com/docs/en/headless), [CLI tool restrictions](https://code.claude.com/docs/en/cli-reference).

## Identity, policy and source invariants

Browser users have individual password logins. Founder-configured capability sets cover `manage_members`, `manage_policy`, `read_map`, `read_evidence`, `contribute`, `correct` and `answer_founder`; owner/contributor/reader are editable presets. operador is an ordinary separately granted member. Each device receives its own revocable, hashed bearer credential, restricted to its company, participant and allowed operations. Team invitations are expiring, single-use and contain no owner token. Server identity comes from authentication; a payload cannot impersonate another participant. Capture participant and inferred task performer remain separate: observing Alice enter a payment does not prove Alice authorized it.

`GET /v1/device-policy` returns `policy_version`, `context_version`, `issued_at`, `expires_at`, `screenshots {founder_allowed, member_allowed}`, learned `work_signals` and device/member restrictions. Signals include source-linked company activities, tools, record patterns and vocabulary; app identity alone is not proof of company work. Classifier categories are `company`, `personal`, `uncertain`. Only company-classified evidence is uploaded; uncertain content remains in a visible local quarantine with counts/reasons and a safe context-resolution path, while personal content never becomes company knowledge. A sanitized `POST /v1/context-gaps` signal may ask for classification context without transmitting the quarantined content; its local event reference never pretends to be remotely available evidence. Ambiguous business purpose for already-company activity **does** upload provisionally and create a Nora question. Founder-derived work signals adapt after answers; they are not a fixed app/window allowlist. Policy expiry/offline behavior must fail closed for screenshots. Both collector and server enforce the screenshot decision; no recording permission is requested when disabled. These controls require OS-level tests, not just stored flags.

All accepted sources are immutable, company-scoped and inspectable under source permissions: observations, founder interview answers, Nora answers and corrections. Store exact text or a private attachment plus SHA-256, source reference, capture time, receipt time, author identity, provenance type and availability. Do not serve evidence as public static files. Derivatives retain source restrictions. Use field-level claims with `basis: observed|reported|inferred`, evidence IDs and a checked excerpt/reference; generated inference is never relabeled as observation.

## Versioned wire contract

JSON uses `schema_version: 1`, UUID string IDs and UTC timestamps; schedule calculations additionally use `America/Sao_Paulo`. Authentication determines the company/member/device. Server rejects forbidden extra identity fields and unknown schema versions. HTTP errors include stable `code`, `message` and `retryable`; validation is 422, denied access 401/403, conflicting versions or idempotency payloads 409. Offline retries use the same event key with bounded backoff.

| Operation | Required content and effect |
|---|---|
| `POST /v1/observations` | `event_id`, `occurred_at`, `policy_version`, `source {kind, app, record_ref}`, `classification {label, reason, context_version}`, `content {text, sha256}`, optional `screenshot {media_type, sha256, bytes_base64}`. Respond with canonical observation ID, authenticated `inspect_url` and analysis state. Accept only company evidence; verify policy and hashes. `(device,event_id)` is unique: same canonical payload returns the original receipt; different payload is a conflict. |
| `GET /v1/work-items` / `POST /v1/analyses` | Claim authorized interpretation work; submit `analysis_id`, `source_ids`, context/model/prompt versions, proposed nodes/edges/field claims and missing links. Member workers handle their own observations; the founder worker can handle authenticated founder interview/Nora answers. Validate source access, job identity and base version. Raw capture/answers survive analysis failure or an offline founder worker, with a visible pending-analysis gap. Analysis is automatic worker output, never recurring human logs. |
| `GET /v1/map` and `GET /v1/tasks/{id}` | Current nodes, typed edges, tasks, gaps/status, accessible source links and history links; filters support person, activity, date and source record. Explicitly show unobserved areas and pending analysis. Search results enforce the same permissions as source opening. |
| `GET /v1/questions?status=pending` | `question_id`, `task_id`, `task_version`, `observation_ids`, `uncertainty_ids`, observed activity summary, missing connection, grouped context and evidence links. Brain creates these transactionally with the provisional map revision. |
| `POST /v1/questions/{id}/answers` | `answer_event_id`, `base_task_version`, exact answer text. Browser founder identity comes from session; channel answers require Nora's verified route/sender mapping, not a submitted `founder_id`. First persist the immutable raw answer and return its ID/application state, before interpretation. Duplicate event has no extra effect; stale versions never prevent durable answer receipt. |
| `POST /v1/map-changes` | `change_event_id`, expected versions, reason/source and typed operations: add, rename, split, merge, reassign, connect, disconnect. Owner/corrector interface invokes this without founder code changes. Reject unsupported source/target IDs. |

For the initial cycle accept a bounded inline PNG/JPEG (proposed decoded limit 2 MiB), with authentication/policy checks before decoding, hash/type checks, private atomic storage and cleanup of failed writes. A local file path cannot substitute for online evidence. A separate attachment service is unnecessary for this first contract. Exact JSON schemas and limits are implementation artifacts to freeze before builders start, not permission to invent incompatible fields.

## Map, interview and answer transaction

Use a flexible typed graph: organization/context, responsibility, job, process, leaf task, person and tracking record. These are representation types, not required departments, a mandatory hierarchy or a preset lifecycle. Many-to-many responsibility and cross-process handoffs are allowed. Onboarding stores attributed founder answers and asks one short next question based on uncovered context: actual activities, people/responsibilities, meaningful stages if any, progress/payment tracking if relevant, and useful documents. A documented explicit “not applicable” is valid; silence is a gap. The answers seed context, nodes and later questions. No company/property facts are preloaded.

A task version contains trigger, input, discrete action, observable result, business purpose, performer, placement, handoffs/tracking connections and per-field supporting claims. `established` is computed server-side only when required fields have supported non-inferred claims, required connections are resolved (including explicitly none/not applicable), and no unresolved contradiction remains. Otherwise it is `provisional` with named gaps. A missing business link has one active uncertainty/question key per task/field/context, so a retry cannot create duplicate questions. Task performer may remain unknown even though capture identity is known.

Brain owns immutable source/answer records, map versions, uncertainties and canonical question state. Nora owns slot calculation, durable rounds/delivery receipts, trusted sender mapping and channel retry. Nora reads pending questions through a narrow service credential and submits authenticated answers; it cannot grant membership or rewrite evidence. Scheduling/outreach authorization remains with the leader/operador.

Persist authenticated raw answers/changes first, independently of task version or model availability. Then validate source/schema and interpret outside a transaction. In one short application transaction, compare expected versions, append task/edge versions, record application of the existing source, link all evidence, recalculate gaps/status and resolve or update questions. Unapplied answers remain pending and retryable. An answer against a stale base is retained and visibly marked for reconciliation; it never silently overwrites newer understanding. A conflicting claim stays attributed beside its predecessor and opens a conflict question. An explicit later correction may supersede a prior claim while retaining both. Split/merge preserves predecessor/successor IDs and a complete source/answer allocation; reject plans that omit evidence, and preserve shared evidence when relevant to multiple successors. No destructive task rewrite is needed.
