# Desktop capture and installation: bounded feasibility recommendation

Status: initial contract recommendation, retained for provenance. Current implementation/review repairs are documented in `docs/setup/desktop-local-layer.md`; the original feasibility receipt remains unchanged. Owner: codex-desktop. Criteria: Q2 (automatic company evidence reaches the authenticated brain and screenshot policy is enforced) and Q3 (founder/team installation, normal work, first cycle and recovery on Windows/macOS).

## Recommended implementation

Deliver one Python application with a durable SQLite outbox, a small macOS Swift helper and a Windows PowerShell/.NET helper. Use native OS interfaces rather than installing a second continuous recorder. Poll the active application/window and its accessible document context; on changed company-related content collect bounded text and, only when permitted, one image of that window. Upload through the brain's authenticated observation API. Register a user-session launch agent on macOS or an interactive logon task on Windows. Normal use needs neither a daily summary nor start/pause rituals.

Target macOS 14+ and Windows 11 initially. Those are proposed minimums, not a claim about the founder's device. The setup must detect and report an unsupported OS instead of silently continuing. Python 3.12+ is the shared runtime; the installer must locate an existing supported interpreter or install the official per-user distribution with human approval where the OS requires it. Source installation on Mac also needs Apple's Command Line Tools to compile the helper; the preferred delivered bundle includes a prebuilt helper so the founder does not install a development toolchain. Signing/notarization and a distributable download URL remain release work, not established prerequisites already satisfied.

### Actual sources and boundaries

| Source | macOS path | Windows path | What it contributes / limitation |
| --- | --- | --- | --- |
| Active app and window | NSWorkspace and focused AX window | GetForegroundWindow + GetWindowText + process identity | Context/timestamps; app time alone does not identify a business action. |
| Visible document text | Accessibility API, excluding protected fields, bounded to active window | UI Automation TextPattern/ValuePattern, excluding password elements | Text exposed by each app; custom canvases, protected desktops and inaccessible content remain gaps. |
| Optional image | ScreenCaptureKit single-window filter; local Vision OCR | PrintWindow for that HWND; UIA text accompanies image | No full-desktop fallback. PrintWindow delegates rendering to the app and may block/fail/return unusable GPU content. Time out the helper and expose the failure. Windows OCR is not assumed delivered. |
| Claude Code | Project-scoped UserPromptSubmit/Stop hooks; bounded new user/assistant text | Same hook contract with an OS-specific command | Automatic after setup in a company project. Never upload full account histories, thinking blocks, arbitrary tool outputs or secrets. Preserve unrelated hook settings. |
| Other AI clients | Their visible accessible text/image under the same policy | Same | No claim of complete Claude consumer app, ChatGPT, API or mobile history. A proxy would cover only requests actually routed through it and is not a subscription-chat capture solution. |

No keyboard logger, microphone recorder, browser password extraction, broad filesystem/history scan, or inspection of the operator's existing AI transcripts is needed for this recommendation. Work on a phone, in person, in inaccessible applications or outside configured company sources remains explicitly unobserved. This cannot be called comprehensive company observation.

## Work context without a fixed window list

The brain's adaptive conversation supplies versioned company context: founder-described activities/tools, participant responsibilities, company/document names and record references actually provided. Application identity is a weak signal; a company record reference plus matching described activity is stronger. The desktop classifier records the actual matching signals and policy version. It does not turn a title such as “Google Sheets” into a certain company activity, nor invent that an invoice was paid.

Use disjoint capture states: company-related; uncertain; excluded. Excluded data is not queued. In the delivered local layer, uncertain title/body/reference content is neither stored nor uploaded, and no image is captured. A sanitized coverage signal (app/source type and missing connection, without a private title/body) can enter the brain for Nora to ask which business context is missing. Company-related text can enter a provisional task even when its purpose/input/result is still unknown. A founder answer changes the versioned context; collectors refresh it automatically. No participant maintains an app/window allowlist. The classifier's recall, mistakes and apps it cannot read must remain visible in verification and pilot coverage.

Screenshots need two independent gates: founder policy authorizes the participant class, and the current surface has company-work evidence. Unknown/missing/expired policy means no screenshot; “team screenshots=false” must disable the native image call itself, not only discard uploads later. Founder screenshot permission is configured separately from the team decision. Recheck the same window identity immediately before capture to handle focus changes. A single-window capture avoids unrelated desktop windows, but personal content inside a company document/app can still be misclassified; this is a real limitation, not perfect filtering.

## Brain contract to consolidate

Aligned with codex-company-brain's room message #58:

* `GET /v1/device-policy`: bearer-authenticated device identity; returns schema/version, policy expiry, screenshot decision for this participant, learned company signals and allowed contribution capabilities. The server determines company and participant from the credential.
* `POST /v1/observations`: immutable event with stable UUID `event_id`, `schema_version=1`, device UUID, observed UTC times, source kind, app identity, bounded record locator/text, classification with matched signals and policy/context version, original evidence SHA-256, and optional image evidence. Same identity+event UUID+same payload returns the same observation ID; changed payload conflicts. Server auth determines performer and company, never a participant ID supplied by the device.
* Image transport follows the brain's shared authenticated attachment upload and opaque attachment IDs, with original hashes preserved. Do not embed a second image schema in observations. A local path is not remote evidence. Upload success alone is not an accepted observation.
* An acknowledgement includes observation ID and inspect URL. The collector marks the outbox item delivered only after that receipt. Device tokens permit ingestion/policy access only; they are not founder browser sessions and cannot read other participants' material.
* Connection failure retains the same queued event ID for retry. 401/403, policy expiry/revocation and malformed data are distinguished in a human-readable health status. No retry storm, fabricated success or recurring manual forwarding. Expired screenshot permission stops new image capture; policy revocation must also suppress queued image uploads.

The final common schema belongs to the brain owner. Disjoint ownership aligned by leader message #91: desktop owns `company_pilot/desktop/`, `install/`, `tests/desktop/`, `scripts/feasibility/mac-capture-probe.swift`, and `docs/setup/`; brain owns the shared package's service/auth/storage/context/map/API schema; Nora owns scheduling/delivery/answer adapter. Leader owns release integration and proposal. This document does not create a second observation model.

## Installation and first-use contract

Deliver commands for `install`, `configure`, `doctor`, `status`, automatic `run`, and `uninstall` as actual software before writing the final setup Markdown. Proposed command names are not instructions to run today. Founder setup configures the online brain, roles including operador, Nora identity and team screenshot decision; device enrollment gives each person a separate credential. Generated team Markdown carries the company URL, policy reference/version and installation procedure, never a founder token, reusable invitation or shared device secret. Founder changes propagate through policy fetches rather than copied prose alone.

Mac human steps: approve the delivered app under Accessibility for active-window text and Screen Recording only if screenshot capture is enabled; approve login/background execution if the OS asks. Do not infer permission from absent window titles. Windows human steps: approve the download/runtime if requested, enroll the logged-in user, and allow the interactive scheduled task. Running as SYSTEM cannot observe the user's desktop and is not a valid installer success. Enterprise device policy can block execution or capture; report the exact check that failed.

After installation the founder performs one actual company task, checks its received observation in the online brain, sees the provisional task and source-linked question, answers Nora in the next authorized round, then opens the revised map and its preserved evidence. Do not insert an out-of-schedule onboarding message. Setup health must separately report runtime installed, autostart registered, permission ready, device enrolled, queue delivered, online retrieval permitted and Nora cycle complete.

Recovery must be concrete: permissions denied → show the exact system setting and rerun doctor; device enrollment rejected → replace only that device credential through founder access; offline → retain bounded queue and retry automatically; native capture timeout/blank content → continue with available evidence and flag the gap; shared runtime changed → identify a missing executable without reinstalling silently; service stopped → show the registered task and restart command; policy changed → fetch and apply before new screenshots. Uninstall disables only the pilot's own service/hooks and preserves user documents. Data deletion is a separate explicit action.

## Verification receipt and stopping condition

The current host is macOS 15.7.4 arm64 with Python 3.15.2, Node 22.23.2 and Swift 6.1.2. No Windows runtime is available here. `scripts/feasibility/mac-capture-probe.swift` is a narrowly scoped development probe: it renders synthetic text off screen, OCRs that image, checks existing permissions without requesting them, and only when Screen Recording is already granted tries capturing the exact window owned by its own PID. It never captures another app/window or the operator's private activity. An offscreen render is E1, not proof of unattended capture; compilation alone does not prove a permission flow, autostart, reboot or installation.

Actual probe result: Swift compilation succeeded. Existing Screen Recording and Accessibility permission checks were both false, so native screen capture was not attempted and no permission prompt was requested. Synthetic image rendering succeeded, but Vision OCR returned `nilError`. Local OCR is therefore an unresolved implementation issue on this runtime; neither successful OCR nor unattended native capture is established. See [the structured receipt](desktop-feasibility-receipt.json). The probe exits normally to report capability states; its exit code alone is not a passing capture/OCR verdict.

Proposed acceptance mapping to reviewer C1–C8: C1 is actual normal-work OS capture; C2 requires this collector's persisted outbox → authenticated remote receipt/retrieval, replay and denial checks; C3–C8 belong to the integrated brain/Nora chain, with the original observation kept inspectable. Add negative flows for team screenshot false/missing/expired, uncertain personal context, focus race, native-helper timeout, offline restart, wrong-role/device credentials and policy revocation. Reboot/logon, native Windows UI capture and real remote/Nora paths remain separate receipts. Headless Windows CI cannot establish interactive Windows capture.

Stop this assignment after the contract, source checks and probe result. Do not launch broad implementation, install a background watcher, request new device permissions, deploy services or capture client/operador activity before leader consolidation and the applicable authorization.

## Primary sources checked

* [Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit): OS recording permission and content filtering. [Apple capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) supports a single window or display. Local macOS SDK headers confirm the screenshot manager is available from macOS 14.
* [Apple DTS permission guidance](https://developer.apple.com/forums/thread/839069?answerId=898801022): use the explicit preflight permission API; window metadata is not a supported permission detector.
* [Microsoft GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow), [GetWindowTextW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowtextw), [TextPattern](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.textpattern), [PrintWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow): native observation pieces, with app-dependent text/rendering.
* [Microsoft Task Scheduler](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-start-page): automatic logon execution is available; interactive user context still needs implementation/testing.
* [Claude Code hooks](https://code.claude.com/docs/en/hooks): project-scoped hook settings and prompt/turn events. A transcript path is not permission to upload the whole transcript.
* [ActivityWatch watchers](https://docs.activitywatch.net/en/latest/watchers.html): existing cross-platform app/title watcher is a reusable alternative, but app/title events alone do not establish input/action/result.
* [Screenpipe API](https://docs.screenpipe.com/cli-reference): existing local recording/search API is a reusable richer alternative. It still needs an enforced founder policy and automatic context/upload bridge; installing it alone does not meet Q2. Its wider recording default is not the minimum recommended path here.
