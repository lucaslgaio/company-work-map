## Policy and participant control — P1/P2

`Brain.set_access_policy(requests, event_id, request_reference)` is founder-authorized. Each request is `{actor_id, read_scope, modify_scope, record_categories}`. Read scope: `all|none|selected`; modify scope: `all|none|own|selected`; categories are meaningful founder-supplied names, empty unless selected. These express a request, never a new ACL promise. The returned/snapshotted `access_policy` contains revision, requested identities/scopes, effective native inspection, `pending|unsupported|verified`, and reason codes. Personal-repository support remains owner plus repository-wide read/write collaborators. No branch/folder isolation or contribution-only role is invented.

`Brain.record_access_verification(receipt,event_id)` requires an authenticated owner/admin attestor. `RepositoryAccess.verify_policy(...)` performs read-only native inspection and produces the typed receipt used here; root exposes it through existing owner CLI. The receipt binds repository/identities/request hash and actual rights. An invitation/pending receipt is not verified access. No real API call/invitation is made in this repair. A changed request invalidates old verification. Existing records are not retroactively hidden or erased.

`Brain.set_participation(choices,event_id)` records only the authenticated participant's own choice: `{participating, screenshots, acknowledged_policy_version, local_exclusions_configured, local_policy_sha256}`. Raw personal exclusion terms stay in desktop-private configuration; no personal title/account value is uploaded as a consent receipt. Founder company-wide exclusions remain supported. Founder authority over company access does not supply individual participation/image permission.

`device_policy()` keeps schema1 fields and adds `controls={capture_allowed,reason,access_state,participation,policy_revision}` and source-backed `recognition_markers`. `screenshots_allowed` is company choice AND this person's image choice. Missing acknowledgement, denied participation, stale policy or unsupported/unverified access blocks capture. Desktop enforces the gate before title/body/image persistence and merges local exclusions before company recognition. A new real company starts gated; legacy/synthetic fixture compatibility is visibly labelled, never native proof of consent. Readback exposes requested/effective state, active recognition names, image/text choice and pending blockers.

**CONFLITO DE EXPERIÊNCIA:** a founder policy the personal repository cannot enforce keeps capture pending rather than silently broadening access. That reduces coverage until the founder selects a supported arrangement or a separately authorized architecture exists. The choice remains with the founder.

## Grounded recognition and accumulated context — B3/B11

Analysis adds optional `recognition_markers:[{value,kind,evidence,operation}]`, with `kind=record_name|record_ref|company_alias|business_account`, `operation=add|retire`. Values must be literal grounded names in supplied source text, not full descriptive context, app-only allowlists or inferred facts. Marker identity is stable by normalized value/kind; separate supported names survive one source/topic. `work_signals` becomes the backward-compatible list of active marker values; descriptive context is not itself an active title match. Readback includes source links and unverified recognition explicitly. Extraction quality/model omissions remain separately unproved.

`context_updates` gains optional `mode=add|replace|conflict` and `replaces:[claim_id]`. Current supported claims are stored separately by stable ID; the existing `context[topic]` remains a backward-readable projection of active claims. Additions retain compatible prior facts. Replacement requires explicit founder intent, cited source and supplied claim IDs; omission is not deletion. Scoped `interview_correct` remains an explicit selected-topic replacement entry point. Deferred/conflict question generations retain their existing stale-answer guards. Old context/history/source bytes remain intact.

## Ordinary message and correction targets — B1/B7; Nora B2/B5/B6/B9/P3 seam

`Brain.message_targets(text="",limit=50)` returns current `open_question_ids` separately from bounded active `correction_targets:[{task_id,version,name,evidence_ids,...}]`, including established tasks. Relevant names/record references rank candidates; neither recency nor inclusion selects a target. `context_targets` exposes claim IDs. No fixed business model or supplier-only target rule.

`Brain.record_message(text,event_id,*,source=None,question_ids=None,candidate_question_ids=None,candidate_task_versions=None)` is the new ordinary Nora/CLI intake. `source` uses the existing verified founder-route contract. Candidate task refs are `{id,version}`; receipt freezes source/actor, current question scope, task versions and context/question bases. Explicit Q references may include resolved questions; question selection and task correction scope remain distinct. If candidates are omitted the Brain computes the bounded receipt-time set. Existing `record_answer` remains backward compatible.

The semantic job kind is `message`. Analysis adds optional `message_intent={kind,task_ids,question_ids,delegate_to,disposition,evidence}`. Kinds: `answer|correction|context|dismiss|delegate|chatter|unclear`. IDs must be supplied candidates and evidence must cite the verified raw message. `disposition` is null or `not_company|not_useful|not_now|already_answered`; delegate is an attributed name or null, not a new route. Semantic selection belongs to the restricted interpreter and Brain validation, not a second Nora heuristic classifier.

Correction intent can apply typed `map_changes` to selected established/provisional tasks using frozen/current versions. `chatter` retains the source/receipt without creating a business gap or rewrite. `unclear` gets a bounded tracked attribution question that can name tasks even if they have no open field questions. A dismissal/delegation is recorded on selected questions as `response_disposition={kind,disposition,delegate_to,source_id}`. Genuine task gaps remain provisional/pending; Nora suppresses unchanged dismissed/delegated asks and exposes the owner/waiting state. No direct team send is inferred. A verified not-company answer may resolve a coverage-context question, not erase an unrelated task.

Applied receipt includes intent, selected task/question IDs and `response_disposition`; operator/Nora consumes it through canonical projection. Pending sources/jobs expose candidate/selected question/task IDs for queued-answer suppression. Projection adds `relevant_answer_ids` per actual missing/conflicted field; generic task evidence remains inspectable but does not reset unrelated ask history. `revisit_evidence_ids` is limited to materially changed uncertainty support.

`ingest_context_gap` accepts optional opaque `context_key` from desktop for a stable unknown context without its raw title. Same resolved key does not reopen merely because another sample arrived; a distinct unknown key can create a real gap. No rule turns all future Chrome/email activity into work.

## Payment meaning — B1/B14

Task interpretation adds optional `payment={object,tracking_record}`, each a normal source-backed claim (unknown may be null). Presence means the interpreter identified a payment; it is not inferred from supplier alone. Supported objects create a typed `pays_for` connection to a source-backed work object; supported tracking creates/uses the actual tracking record. An identified payment lacking object or tracking/balance support remains provisional with a specific payment-link question, even if its nine ordinary fields are filled. Existing task IDs/fields are unchanged.

Cross-field contradiction may be represented explicitly with cited alternatives/consistency issues; Brain preserves those as provisional and question-linked. Literal quote validation cannot mechanically prove general business semantics. The original AVM82/CAP14 correction must be shown through ordinary message intake with approval versus execution and old facts/history retained; no keyword-specific construction-company rule.

## Company-record addition — root scope extension #465/#472

`Brain.ingest_company_record(payload)` accepts exactly schema_version=1, event_id UUID, occurred_at timezone-aware ISO, synthetic boolean, source `{system,record_id,url,revision}`, operation `upsert|removed`, content `{text,sha256,complete?}`, and object null or `{storage_ref,sha256,media_type,size_bytes}`. Text is at most 256KiB UTF-8; complete defaults false. Binary/full-file bytes stay in the root watchdog's private archive. The core never dereferences the original URL or archive locator. This does not remove the Git snapshot's existing finite size/growth limits or prove that a whole company corpus fits it.

Founder configuration is `Brain.update_policy({'watchdog_actors':[authenticated_actor_id]},event_id)`; the new-company/default legacy allowlist is empty. Root owns the CLI exposure. Company sources require this actor allowlist plus verified effective human access. They do not require device-participation consent. Legacy synthetic fixtures without an access request remain explicitly E1 compatibility, never real permissions.

The core derives company/logical record/source IDs. Provider identity/revision/url are retained; same revision/hash replays without a commit, changed bytes under one provider revision reject, removals append tombstones and do not delete task support/history. Empty extracts are recorded without analysis. Upserts with text queue company_record, bounded to fifty granular task outputs, supplied task IDs only. Null IDs are stable by source and output index. `record_extraction={complete,limitations}` is required; a partial source cannot be reported complete. File contents establish recorded state, not a witnessed human execution/approval; the core refuses a performer observed solely from a company record. Restricted prompt7 forbids archive/URL reads and author-to-performer inference.

The snapshot adds company_records and the existing source/task/question/view contracts remain readable. Markdown exposes provider revision, source removal, partial extraction and preserved links/history. Full catalog/completeness/change discovery/archive/consumer acknowledgements remain root-owned. No connector, real account export or live service is activated by this core adapter.
